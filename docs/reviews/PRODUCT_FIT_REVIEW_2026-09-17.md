# Trend Top 新增内容适配性报告

日期：2026-09-17。视角：用户体验、产品定位、实现与承诺的一致性。

## 评审范围与结论

基准是我上次提交的 `800bb4d`，对比你已推送的最新版本 `a84637b57652f50267101fc357b9f8d7c203702b`。区间有 8 个提交、32 个文件变化，分析时忽略行尾格式变化。已获取远端代码，没有覆盖本地工作区，没有修改业务代码，没有打开或检查网站页面，也没有运行新版测试或构建。界面判断仅使用你提供的截图；数据库实际内容、线上性能、第三方采集成功率均未验证。

**整体方向符合网站定位，建议保留新增功能，但当前实现尚不适合完整验收。** Use case 帮用户回答“用它做什么”，关注列表帮用户持续跟踪项目，类型专属对比和安装量补充帮助用户做选择。这些都比单纯增加收录数量更有价值。

主要问题不是功能太多，而是分类、指标和付费承诺尚未完全对齐：用途筛选可能漏结果；安装量可能错配到同仓库的多个 Skill；关注列表的排名范围和错误反馈不完整；新采集容错可能把未知数据写成零。

优先级定义：P1 是影响结果正确性、付费功能可信度或关键操作反馈的问题，建议先处理；P2 是信息组织、措辞和扩展性优化。以下“代码确认”表示控制流程或数据处理在代码中可直接看到，不代表在线上复现过。

## 二、Use case：应保留，但目前还需要调整

### 1. 用途名称混合了任务、技术和资源形态（P2）

当前 14 个可选用途包括 Browser、Database、Git、GitHub、Directory、Playground、Spec 等。它们并不处于同一层级：Database 是领域，GitHub 是平台，Directory 是网站形态，Research 才比较接近用户任务。

这会让用户仍然需要理解分类规则。例如“数据库 MCP”容易理解，但“Git”和“GitHub”之间怎么选、“文档”是否包含 PDF 和表格，并不清楚。

建议界面保持英文 `Use case`、中文“用途”，显示更接近动作的名称，例如“网页自动化”“数据库操作”“文档处理”“代码开发”“资料研究”“界面构建”“文件管理”“身份认证”“资源发现”。Git/GitHub 可以先合并成“代码协作”；Directory/Playground/Spec 可以作为网站形态或次级标签，避免都挤进用途菜单。不增加第七种资产类型。

分类可以继续使用内部 category，但不要把 category 再做成与 Topic、Use case 平行的第三套主导航。详情页目前又同时展示用途、category 和 Topic，可能出现“Documents / Docs / documents”这种语义重复；五个 Topic 的上限不能解决跨字段重复。

证据：[用途定义](https://github.com/liangwenli1/trend-top/blob/a84637b/shared/taxonomy.js#L1)、[详情标签](https://github.com/liangwenli1/trend-top/blob/a84637b/src/pages.jsx#L517)。

### 2. 仓库用途筛选在分页后执行，可能漏结果（P1，代码确认）

`github-repo` 先调用原仓库排行榜获取一页，再对这一页过滤 Use case，`total` 也改成过滤后的这一页长度。

例如当前第一页十个仓库都不是文档用途，后面有大量文档项目，选择“文档”仍可能得到空列表或错误总数。用户会误以为网站没有收集这些项目，加载更多也可能提前结束。

建议在完整候选集上完成用途筛选，再排序、计数和分页。榜单、搜索、Charts 和详情里的用途链接应使用同一套过滤口径。

证据：[仓库用途过滤与 total](https://github.com/liangwenli1/trend-top/blob/a84637b/server/catalog.js#L384)。

### 3. 老数据没有用途回填，显示分类与筛选可能不一致（P1，代码确认）

这次迁移新增 `assets.use_case`，但没有看到存量记录的统一回填。展示时 `classify()` 可以即时推断用途；筛选时 SQL 却直接使用 `WHERE use_case = ...`。

因此，尚未重新采集的老记录可能在详情页显示“数据库”，点击这个用途却筛选不出它。是否已经影响线上，取决于现有数据是否全部更新过。

建议为存量数据执行一次有版本记录的分类回填；后续规则更新也应有重分类机制，而不是等待每个条目碰巧再次被采集。低置信度保持“未分类”，不要为了填满菜单强行归类。

证据：[新增字段](https://github.com/liangwenli1/trend-top/blob/a84637b/server/db.js#L118)、[展示时推断](https://github.com/liangwenli1/trend-top/blob/a84637b/shared/taxonomy.js#L92)、[SQL 用途过滤](https://github.com/liangwenli1/trend-top/blob/a84637b/server/catalog.js#L445)。

### 4. 截图中第七个筛选控件单独换行（P2，截图与代码确认）

新增 Use case 后共有七个控件，桌面 `.filters` 仍按六列布局，所以 Project age 独自落到第二行。截图已经能看到这个问题，也浪费了列表上方的空间。

建议第一层保留搜索、排序、时间窗口、用途；Language、Topic、Project age 放进“更多筛选”，显示已启用条件数量，并提供清除筛选。继续沿用方框、细边线、黑白和蓝色强调，不需要换 UI 风格。相比把七列全部压窄，这样更适合中英文和较小屏幕。

### 5. 页面搜索与顶部搜索的能力不一致（P2，代码确认）

顶部搜索使用用途/类型扩展；榜单里的搜索框虽然改成“名称、用途或类型”，非仓库资产的 SQL 仍只匹配名称、简介和 category，没有相同的扩展流程，也没有直接匹配 `use_case` 或类型。

建议两处共享检索规则；否则榜单搜索提示应回到实际支持的“名称或简介”。同时避免短词的子串匹配，例如英文 `ui` 可以命中普通单词里的字符，类型词也不应在没有明确选择时直接缩小整个搜索范围。顶部扩展搜索现在每种类型最多发起五次排行榜查询，六类情况下最多三十次调用，这是性能风险；没有线上计时，不能认定它已经导致当前加载慢。

证据：[榜单搜索 SQL](https://github.com/liangwenli1/trend-top/blob/a84637b/server/catalog.js#L440)、[扩展检索](https://github.com/liangwenli1/trend-top/blob/a84637b/server/catalog.js#L714)、[关键词匹配](https://github.com/liangwenli1/trend-top/blob/a84637b/shared/taxonomy.js#L236)。

### 6. 榜单用途与邮件推送用途还没有打通（P2，代码确认）

目前推送设置仍保存类型、榜单、语言、Topic，没有 Use case；摘要生成也没有按用途过滤。语言/Topic 继续通过共享规范化处理，并不需要把它们改名成用途，但“在网站选了文档处理”不会自动变成邮件偏好。

这不是现有 Pricing 文案的直接违约，因为 Pricing 只承诺语言和主题筛选。不过用途成为主发现入口后，建议邮件偏好增加同一套用途选项，让用户无需重新用技术 Topic 拼出任务范围。

证据：[推送偏好](https://github.com/liangwenli1/trend-top/blob/a84637b/src/subscription.jsx)、[摘要生成](https://github.com/liangwenli1/trend-top/blob/a84637b/server/digest.js#L48)。

## 三、Pro 新增内容：价值合理，交付边界要更明确

### 实际增加了什么

这次 Pro 主要新增 **Watchlist（关注列表）**，不是重做一个订阅体系。每日邮件、邮件图表、语言/主题过滤、发送时间和时区在基准版本中已经存在。月付与年付仍是同一个 Pro 权限，功能相同。

Pricing 已明确介绍每日摘要、关注列表、邮件内置图表和推送筛选。没有看到新增油价数据或油价邮件能力；此处 Pro 的内容是开源项目热点。

“关注列表”有数据库和 API，新增、读取、删除要求有效 Pro，权限不是仅靠前端隐藏。现有付费续订与邮件推送继续独立管理，这是正确的产品边界。

证据：[套餐功能文案](https://github.com/liangwenli1/trend-top/blob/a84637b/server/billing.js#L16)、[Pricing 介绍](https://github.com/liangwenli1/trend-top/blob/a84637b/src/billing-ui.jsx#L34)、[关注接口权限](https://github.com/liangwenli1/trend-top/blob/a84637b/server/watches.js#L115)。

### 1. “名次变化”缺少排名范围，且结果不完整（P1，代码确认）

关注列表固定查各类型的 `hot + week`，不是用户关注时正在看的榜单或筛选结果。页面没有交代这个口径。

接口请求 `limit: 200`，但非仓库排行榜把 limit 最大限制为 50，所以这些类型实际只检查前五十名。前五十名之外的项目会得到空排名，无法兑现一般用户理解的“关注后看到名次变化”。

建议第一版统一采用“该类型周热门榜”，在界面明确标注，并为任意被关注条目计算完整榜内名次；无评分历史、未入榜、排名下降出榜应分别说明，不能全部显示横线。第一天提示“已开始跟踪，下次更新后显示变化”。

证据：[关注排名快照](https://github.com/liangwenli1/trend-top/blob/a84637b/server/watches.js#L14)、[列表排名](https://github.com/liangwenli1/trend-top/blob/a84637b/server/watches.js#L70)、[排行榜 limit 上限](https://github.com/liangwenli1/trend-top/blob/a84637b/server/catalog.js#L490)。

### 2. “距上次访问”实际是读取关注列表时重置（P2，代码确认）

默认 GET 关注列表会立即更新全部条目的已读快照。这并不等于用户上次访问整个网站；响应尚未成功展示时，基线也可能已经被更新。

建议文案改为“自上次查看关注列表以来”，展示对比时间与最新采样时间。返回数据后，成功展示再单独标记已读，避免请求失败导致变化被吞掉。网站关注变化与邮件“相对上封摘要的变化”可以同时存在，但要写清两个不同的比较基准。

证据：[读取时写入快照](https://github.com/liangwenli1/trend-top/blob/a84637b/server/watches.js#L106)。

### 3. 关注失败没有提示，取消关注未检查响应（P1，代码确认）

详情页关注失败会恢复按钮原状态，却不显示原因；达到一百条上限也会像没有反应。关注列表取消关注时，没有检查 HTTP 是否成功就直接从界面移除。

建议保留当前按钮风格，补充成功/失败状态、重试和上限说明。失败时不要显示操作已经完成。Pro 到期后可以锁住新的跟踪计算，但建议允许查看已保存项目和取消关注，避免用户连整理自己的列表都需要重新购买。

证据：[详情关注错误处理](https://github.com/liangwenli1/trend-top/blob/a84637b/src/pages.jsx#L575)、[取消关注](https://github.com/liangwenli1/trend-top/blob/a84637b/src/subscription.jsx#L306)、[到期删除权限](https://github.com/liangwenli1/trend-top/blob/a84637b/server/watches.js#L130)。

### 4. 关注与摘要目前是两项并列功能（P2）

没有看到 Watchlist 被接入摘要选取。用户关注某项目，不代表邮件一定会出现它。这与目前较克制的 Pricing 介绍基本一致，但应明确说明，避免用户把“关注”理解成“邮件必推”。

建议后续提供“把关注项目加入每日摘要”的可选项，仍每天最多一封；不必现在扩大成即时告警。历史、告警、导出等未来能力继续放在路线图，不写成已交付的 Pro 权益。

“每封邮件内置增长图表”也建议改成“摘要含榜单图表；有历史数据的领先项目附增长曲线”。现有曲线选择受历史数据和榜单顺序影响，没有数据时不应为了兑现绝对措辞制造曲线。

## 四、评分与采集：本次最需要先修的部分

### 1. Skill 安装量按仓库匹配，资源粒度错误（P1，代码确认）

目录采集虽然取到了条目 `name`，实际匹配却只使用 `type + GitHub 仓库`，然后把一条目录计数写给这个仓库下所有匹配资源。

一个仓库可能同时有 PDF、表格、前端等多个 Skill，各自安装量不同。当前逻辑会让它们共享计数；同仓库有多条目录记录时，最后处理的记录还会覆盖前面记录。新建资源时，也把该目录条目的计数写给遍历出的多个 Skill。

建议按“目录资源标识 + 仓库 + Skill 名称/路径”匹配。只有仓库级指标时，明确标注仓库级，不作为单个 Skill 的安装量。如果不能可靠对应，宁可不填。

证据：[目录匹配与全量写入](https://github.com/liangwenli1/trend-top/blob/a84637b/server/website-sources.js#L170)、[新建 Skill](https://github.com/liangwenli1/trend-top/blob/a84637b/server/website-sources.js#L213)。

### 2. 不同来源的指标混用，且旧信号可能丢失（P1，代码确认）

安装量、下载量、usage 共用一个评分入口，但累计安装与近期下载不是同一统计口径。数据只记录目录和更新时间，没有统一的统计窗口、计量单位与资源粒度，也没有用量历史序列。

常规 `upsertAsset` 会覆盖整个 `ranking_signals`，目录采集随后补写。因此目录本轮失败或未再返回该条目时，先前的用量可能丢失，排名可能突然切回纯 Star。多目录记录还基于预先读取的旧 JSON 合并，不能可靠保留全部来源。

建议独立保存各来源指标，记录值、单位、累计/周期、采样时间、粒度、可信度和新鲜度。定一种当前有效的评分口径，再提供回退规则。用量缺失不能等同于无人使用，零也不能转换成“未知”。

55% 热度 + 45% 用量可以作为可解释的试验公式，但现在不足以声称代表“最好用”或真实用户数；同一类型内也应尽量使用可比数据。

证据：[指标选择与零值处理](https://github.com/liangwenli1/trend-top/blob/a84637b/server/catalog.js#L152)、[类型评分](https://github.com/liangwenli1/trend-top/blob/a84637b/server/catalog.js#L107)、[覆盖 ranking_signals](https://github.com/liangwenli1/trend-top/blob/a84637b/server/jobs.js#L228)、[目录信号合并](https://github.com/liangwenli1/trend-top/blob/a84637b/server/website-sources.js#L145)。

### 3. “官方”证据仍存在语义和字段问题（P1）

代码把“收录于 Official MCP Registry”直接等价为项目“Official”。注册表的名称与项目是否由原厂维护是两个不同事实，至少应该分别表达，不能仅凭目录名称推导厂商身份。

另外独立 Website 保存时传入 `source.trust`，而来源表存储、读取使用 `trust_level`。这可能让官方网站缺少预期证据。此字段不一致可直接从代码确认，实际影响需结合来源数据判断。

建议显示两个独立标记：“厂商官方”和“已收录于 MCP 注册表”。证据记录来源 URL、验证方式、验证日期；不把“Verified”用于仅根据组织白名单或页面提及得到的推断。修正 Website 字段对齐。

证据：[官方判断](https://github.com/liangwenli1/trend-top/blob/a84637b/shared/taxonomy.js#L117)、[Website 来源字段](https://github.com/liangwenli1/trend-top/blob/a84637b/server/website-sources.js#L245)。

### 4. 独立 Website 没有用量时从热门榜消失（P2，代码确认）

移除旧的信任/新鲜度热度分是正确的，但独立来源没有 usage 时 score 为 null，默认热门榜又排除 null。Website 元数据采集本身并没有为这些来源写入用量。

因此“已经收集 21st.dev”与“用户能在默认 Website 榜单找到它”仍可能是两回事。建议在 Website 提供独立的“精选网站/全部网站”入口，无数据条目仍可被搜索和浏览，并标注“暂无可比较热度”。不要把关联仓库 Star 说成网站访问量。

证据：[独立网站计分](https://github.com/liangwenli1/trend-top/blob/a84637b/server/catalog.js#L116)、[过滤无评分条目](https://github.com/liangwenli1/trend-top/blob/a84637b/server/catalog.js#L479)、[Website 保存指标](https://github.com/liangwenli1/trend-top/blob/a84637b/server/website-sources.js#L275)。

### 5. 不完整仓库 hydration 失败后仍写零与当前时间（P1，代码确认）

最新提交允许 code-search 返回不完整仓库。补取完整仓库失败时，除 404 外继续写入；`upsertGithubRepo` 将缺失 Star/Fork 写为零，缺失创建/push 时间写成当前时间，同时生成快照。

这可能让已有热门仓库突然变成零 Star、造成错误负增量，或让老项目看起来刚创建/刚更新。Skill 资产还在完整仓库补取之前写入，后面成功补取并不会在这个流程里直接修正此前资产记录的全部字段。

建议未知元数据留空或保留旧值，不能生成虚假的零值快照；完成完整仓库校验后再更新计数和日期。失败候选进入重试队列，并把采集运行区分为成功、部分成功、失败。

证据：[失败后继续写入](https://github.com/liangwenli1/trend-top/blob/a84637b/server/jobs.js#L554)、[默认零和当前时间](https://github.com/liangwenli1/trend-top/blob/a84637b/server/jobs.js#L137)。

## 五、类型专属对比与文案优化

新增协议、传输、宿主等字段值得保留。不过当前存在默认推断：插件统一 MCP，组件统一 UI registry / shadcn-compatible apps；宿主名会从简介关键词推断。资源类别不应自动等同于已验证兼容性，例如一个普通组件库未必兼容 shadcn registry。

建议分成“已验证”“来源声明”“未知”，未知显示横线并说明含义。不要用漂亮的默认值填空。相关字段较多时，先展示最影响选择的协议/宿主/传输/语言，标识和来源放在次级信息里。

证据：[默认协议与兼容信息](https://github.com/liangwenli1/trend-top/blob/a84637b/shared/taxonomy.js#L136)、[对比展示](https://github.com/liangwenli1/trend-top/blob/a84637b/src/pages.jsx#L400)。

| --- | --- | --- | --- |
| HIGH | 关注失败无提示，取消关注不确认响应成功 | 明确成功、失败和重试；失败保留原条目 | 用户必须知道操作是否完成。 |

| MEDIUM | 用途、category、Topic 语义重复 | 区分主用途与技术标签，去掉重复展示 | 控制信息量，避免分类体系膨胀。 |

## 六、推荐处理顺序与验收条件

先保留所有新增功能入口，不继续扩功能。第一批修复数据正确性：不完整仓库写零、Skill 目录粒度、指标来源保存、存量用途回填、仓库分页前筛选。第二批完成 Pro 关注列表：完整排名与范围说明、操作错误反馈、正确的已读基线、到期后保留整理能力。第三批再整理筛选布局、分类命名、对比字段和 Website 无评分入口。

建议下一次真正验收时重点覆盖：

1. 同仓库两个 Skill 的安装量不同，不能被互相覆盖。
2. 一个老记录详情显示某用途，点击用途仍能检索到该记录。
3. 用途匹配项目位于原榜第二页以后，筛选后的总数与分页仍正确。
4. 第五十一名之后的非仓库项目也能显示完整名次；无排名有明确原因。
5. 关注达到上限、网络失败、取消失败都能恢复且有反馈。
6. 第三方目录失败不丢已有指标，GitHub 补取失败不写零快照。
7. 相同评分窗口与同粒度指标可比较，来源和时间对用户可见。
8. Pricing 写出的 Pro 权益与实际行为一致；关注项目是否进入邮件写清楚。
9. 桌面、手机、200% 缩放与长中英文标签的筛选布局合理。

以上是后续验收条件，本次未执行这些测试。新版已有新增分类、评分、检索和关注测试，但从测试代码看，尚未覆盖多个关键边界，不能用基础用例替代上述检查。

**评审结果：方向通过；完整验收暂不通过（Block）。** 原因是仍有 HIGH 级操作反馈/兼容性表述问题，以及影响筛选、资源指标和关注排名可信度的 P1 问题。继续沿用现有视觉风格即可，当前不需要重做 UI 或增加新的顶层资产类型。
