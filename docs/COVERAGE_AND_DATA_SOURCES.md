# 热门资源覆盖检查与数据来源

更新：2026-09-17。本批对应开发计划 P0-5 和 P0-6 的工程基础，不代表已经核对完所有来源的许可，也不代表线上漏收已经自动修复。

## 管理员怎么检查漏收

登录管理员账号，从头像菜单进入网站管理，找到“热门资源覆盖”，点击“检查覆盖”。后台读取当前部署所使用的数据库，对照 16 个固定样本，覆盖仓库、Skill、插件/MCP、Agent、组件库、网站六种类型。

固定样本登记在 `shared/catalog-benchmark.js`。目前包含 Firecrawl、Playwright、Supabase、Anthropic 的 PDF/frontend-design Skill、Firecrawl/GitHub MCP、Codex、Claude Code、shadcn/ui、Radix，以及 21st.dev、Skills.sh、Smithery、Glama 等。

`awesome-design-md` 暂时按完整仓库名匹配，不猜测 owner，不匹配 `awesome-design-md-tools` 等近似名称。确认目标项目的唯一 owner/repo 后应把样本收紧为该身份。样本是人工维护的期望集合，不是实时热门榜；修改时递增版本，避免前后覆盖率失去可比性。

| 状态 | 表示什么 | 后续处理 |
| --- | --- | --- |
| 已收录 | 目标类型中有有效条目，类型证据满足检查规则 | 查看是否还需要改善更新时间或内容完整度 |
| 仓库已收录，目标资源缺失 | 只找到父仓库或其他 Skill 文件，没有指定目标资源 | 检查 SKILL.md 路径、树验证、分页或资源拆分 |
| 在其他类型中 | 同一身份有条目，但不在预期类型 | 核对真实产品用途；不要为了覆盖率把同一仓库复制到所有类型 |
| 类型证据不足 | 存在旧条目，但没有验证记录 | 检查实际资源证据，不能把 README 搜索命中当作已验证 |
| 已停用 | 历史条目被停用、删除或归档 | 查看分类审核原因和采集依据，保留历史以便排查 |
| 候选待审核 | 管理员候选队列里已有对应目标 | 完成审核与采集，不重复提交 |
| 来源已登记，未形成条目 | Website 已在来源表，没有对应资产 | 检查是否到采集时间、是否启用采集、是否保存成功 |
| 站点采集失败 | 来源表记录了实际抓取错误 | 查看错误、限流及重试时间 |
| 来源已停用 | 来源登记项被管理员停用 | 确认是否有意停用 |
| 未收录，原因未确认 | 数据库没有足够记录定位原因 | 查看最近采集查询日志，必要时添加针对性查询或人工候选 |

查询失败或限流会作为最近一轮采集的上下文返回。它不能直接证明某个具体项目的漏收原因。完整的逐候选采集轨迹、淘汰原因统计仍需后续开发。

覆盖数字是“这组固定样本中有多少被收录”，不能对用户宣传为全部热门资源覆盖率。Demo 模式明确标注演示数据库结果；本次未访问生产数据库，未取得线上实际覆盖数字。

## 导出并比较前后结果

在 Ubuntu 服务器仓库目录执行，使用已有配置包装器，避免手动填写数据库密码：

```sh
docker compose exec -T app node scripts/apply-config.mjs node scripts/catalog-coverage.mjs > coverage-before.json
```

调整采集规则并按正常流程运行采集后，再比较：

```sh
docker compose cp coverage-before.json app:/tmp/coverage-before.json
docker compose exec -T app node scripts/apply-config.mjs node scripts/catalog-coverage.mjs --baseline /tmp/coverage-before.json > coverage-after.json
```

新报告包括新增覆盖、覆盖退步、状态变化。比较要求版本、样本 ID 和数据库模式一致。报告文件只保存管理员排查资料，不应放进公开静态目录。

本地已经配置好 `.env` 的开发环境也可使用：

```sh
npm run catalog-coverage -- --output coverage-before.json
npm run catalog-coverage -- --baseline coverage-before.json --output coverage-after.json
```

检查逻辑不自动新增或停用资源，不修改榜单计数。命令沿用项目公共数据库启动流程，启动时仍可能执行既有幂等迁移与回填；“只读”指覆盖检查本身。

## 来源登记与展示口径

统一登记在 `shared/data-sources.js`，采集端的 Website 来源和目录 URL 从此读取，避免后台说明与实际采集地址漂移。后台展示来源、读取方式、计划频率、保存内容边界、已有抓取时间和错误，以及条款审核状态。

- **GitHub**：仓库元数据、Star、Fork、带日期的增量。Skill 文件和组件资源的关联仓库 Star 是仓库指标，不能当作它们自己的安装量。
- **Skills.sh**：只把明确的单个 Skill 安装量关联到匹配资源；记录统计窗口和采样时间，未说明时标记未知。
- **Glama**：只保存实际展示的用量或下载计数；质量评分、描述中的用户数量暗示不能当作使用量。
- **Official MCP Registry**：目录身份与仓库关联。入选注册表不等于经过本网站的厂商身份验证。
- **21st.dev、Smithery、Agent Skills、shadcn/ui**：目前登记内容以网站元数据和链接为主；不能据此宣传已经抓取所有组件、托管连接能力或真实站点访问量。
- **Firecrawl**：负责页面抽取，是工具提供方，不是被抽取计数的原始来源。详情页引用实际网站、目录或 GitHub。

详情页展示来源链接、抓取时间、指标的统计对象、统计窗口和采样时间。来自旧数据且缺少来源记录的目录计数仍明确显示来源/窗口未知，不伪造“累计”或“每周”。独立 Website 元数据条目不展示虚构的 GitHub 指标。

所有来源条款审核目前为 **pending**。GitHub 条款入口已登记；其他来源的适用条款和逐资源许可证尚未完成核对。不把公开可访问、robots 允许或代码开源视为目录指标、图标和完整内容可任意再分发。登记的保存边界是本项目的工程约束，不是法律许可结论；存储期限与删除流程仍待补齐。

下一步还需要隔离不同目录、计数单位与窗口的用量评分，以及校准其权重。新增来源说明不应被描述成已经统一了跨目录排名的可比性。

## 修正“数据不足被显示为零”

过去资产增量聚合使用 COALESCE，将空增量当作 0。即使只存在上一窗口的数据，当前窗口也可能被显示为增长 0。

现在对所选日/周/月窗口分别统计有效天数：

- 所选窗口每一天有已知增量时才计算该窗口总增量。
- 全部日期都明确记录 0 时，正确显示真实的 0。
- 缺少日期、日期存在但值为 NULL、仅上一窗口存在记录时，当前增量保持缺失。
- 上期窗口独立验证；上期不足不会变成“上期为零”。

增长榜可能因此少一些条目，这是移除了不可靠的增长信号，并非删除了收录数据。累计 Star 榜仍可查看这些条目。周数据不足时，不能靠改标签把它当作完整一周的增长。
