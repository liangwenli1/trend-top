## 2. 任务、发布和失败恢复

生产架构仍使用 PostgreSQL、API 与 scheduler。scheduler 每日 02:00 UTC 后检查采集，每小时独立检查到期邮件；错过采集时间可从数据库状态恢复。同类任务取得 180 秒租约，每 30 秒续期。丢失租约的 worker 不再发布；队列请求记录自己的 worker 身份，旧 worker 不能覆盖替换 worker 的状态。

后台采集、摘要和指标重建按钮现在返回 202 并写入持久队列，避免浏览器一直等待长抓取。相同任务处于排队 / 执行状态时合并请求。已知任务失败最多三次、间隔五分钟重试；被其他同类任务占用时延期，不消耗失败次数。队列自动消费需要 PostgreSQL，不能用多个进程并发打开同一个 PGlite 目录。

网络阶段暂存验证通过的仓库、资源、快照、Star 历史及成功来源观测。发布阶段在一个数据库事务中写入目录、重建派生指标、复制关联仓库指标、完成运行记录并生成发布版本。失败会回滚，读者继续看到上一版目录。抓取轨迹、来源失败退避、账户操作和租约心跳不放进长时间网络事务。

暂存上限为 60,000 条写操作 / 64 MB；达到上限明确失败，保留旧发布。进程退出会丢失尚未发布的内存暂存，之后重新采集，**没有实现逐页断点续抓**。租约、队列与服务商幂等键也不能构成 SMTP 的“绝对只发送一次”保证。

API 每五秒检查发布版本，发生变化时失效本进程公共缓存及 Similar 原始数据缓存。缓存本身仍有界且短期有效；浏览器已有缓存不是瞬时广播刷新。管理员来源 / 分类 / 关系审核也发布新版本，但后台新鲜度使用真正采集运行的发布时间，避免把配置修改误认为新抓取。

## 3. 覆盖、分类和可操作详情

固定百项池用于回归，不表示“实时最热门一百项”，也不会自动把名单全部插入目录。后台覆盖报告区分已收录、类型不符、待验证、未观察等状态，并按候选身份查看查询、预算、类型验证、GitHub 文件验证、抓取失败、暂存 / 发布轨迹。

Skill 必须验证真实 `SKILL.md` 路径，不能因为简介出现 skills 就复制整个仓库为 Skill。源码收集和产品资源收集分开；正常分类中同产品拥有网站、具体 Skill 或 MCP 是允许的，但必须分别有资源证据。All 搜索展示一个产品家族与其具体资源，避免多张相同简介误导用户。

同组织不等于同产品。后台人工关联须记录主仓库和证据，可以解除；不自动把 Playwright、浏览器工具或任意 API 库当 Agent。已人工下架的条目在后续抓取更新时保持下架；仅更新预览或安装资料不重新启用资源。

`awesome-design-md` 仍需精确 owner / repo 才能核对；不能猜仓库地址然后宣布采集规则已覆盖。人工误分类抽查建议每类二十项，记录规则版本、实际证据与纠正动作。

## 4. 来源许可与指标口径

| 来源 | 当前处理 | 还需要什么 |
| --- | --- | --- |
| GitHub | 原始仓库、日期计数和链接；保留可识别 SPDX / 原作者信息 | 项目许可逐资源核对；关联仓库 Star 不冒充独立 Skill 安装量 |
| Skills.sh | 页面基础资料；增强计数需批准审核；安装量匹配具体具名 Skill / 路径 | API 文档要求 Vercel OIDC；当前 Docker 服务没有该身份适配，不能宣称已接通匿名 API；遵守来源及资源许可 |
| Glama | 硬性停用当前竞争目录数据采集 / 增强指标；后台开关不能绕过 | 需要与权利方单独授权并开发允许的适配器，普通 API Key 不足以解除该限制 |
| Smithery / 21st.dev 等 | 基础来源登记、链接；无明确许可的增强计数不展示 | 核实对应条款及具体资源许可；隐私政策不是数据再发布授权 |

依据 [Skills.sh 条款](https://www.skills.sh/terms)，作者资源仍受各自许可约束，合理缓存不等于获得任意复制权限；其 [API 文档](https://www.skills.sh/docs/api) 指定 Vercel OIDC 鉴权。根据 [Glama 条款](https://glama.ai/policies/terms-of-service) 对竞争目录用途及绕过 API 门槛的限制，当前适配器的竞争目录使用不能仅凭购买 API Key 推定获准，因此代码禁用该路径。

上述是产品实现对官方来源的保守处理，不是替权利方授予授权。管理员审核需记录条款链接、署名、允许方式和依据；该记录用于追溯，不是自动法律认证。

`Hot score` 统一表示仓库趋势代理信号。目录的安装 / 使用 / 下载指标单独保存描述，只有同目录、同单位、同资源范围、同窗口才计算同组百分位；单一样本、未知窗口不生成校准评分。没有关联仓库指标的独立网站不制造 Hot 值。旧匿名增强计数在 live 模式撤下，Demo 明确是样例。

Firecrawl 在允许来源中帮助提取站点内容与元数据，不能提供访问授权，也不创造可信使用量。直接提取与 Firecrawl 路径都检查 robots；robots 明确不存在可以继续，获取失败 / 拒绝则保留旧资料并退避，不绕过限制。

## 5. Pro 摘要、保存筛选和投递

保存筛选规则是**每日检查**：首次执行先建立基线；新条目是新进入相同条件下前五十项候选，不是整个互联网的新项目。增长提醒在候选的相应 Star 增量由低于阈值变成达到阈值时触发；条件、周期或阈值变化会重新建立基线，避免旧条件制造提醒。不是实时警报。

摘要最多十二个产品。关注内容先选，保存筛选变化随后，剩余名额分配给用户选中的类型 / 榜单；具体条目说明命中的偏好或变化。同产品只出现一次。规则建立基线但没有变化时仍保存比较快照，不为填满邮件发送空洞内容。

先持久化完整邮件快照再调用邮件服务商。已知失败复用首次内容；网络超时、进程中断或服务商接收状态不明进入人工核对，不自动重发。管理员可附证据记录确认接收、不重发或允许重试。账户历史中的已接收是服务商接收，不保证用户收件箱送达。

付费有效性与邮件开关在发送前重查。停止邮件不取消 Pro、不退款；取消续费通常保留本期权益；退款请求需交易处理结果，不写成“退款成功”。用户到期后仍能读取 / 删除已保存条件和查看自己的投递历史。

不可变图表只包含匿名趋势数据，不包含用户邮箱或管理链接。邮件正文、文本回退与图片分别保存：图片被屏蔽时，关键数字、窗口和为何收到仍可阅读。

## 6. 数据保留和删除

| 数据 | 自动处理 |
| --- | --- |
| 候选采集轨迹、查询诊断 | 九十天后清理 |
| 已完成 / 已失败的手动任务 | 九十天后清理；排队 / 执行中的任务保留 |
| 验证码 / OAuth 状态 | 过期一天后清理 |
| 登录会话 | 过期三十天后清理 |
| 已发送 / 已跳过邮件正文快照 | 邮件日期超过四百天后清除正文；保留状态记录 |
| 邮件 PNG | 距最后一次用于新邮件超过四百天后清理；同内容再使用刷新时间 |
| 结果不明 / 失败待处理邮件 | 不按已发送正文策略清除，保留恢复依据 |

清理随成功采集执行，不是独立实时销毁服务。资源历史计数为榜单计算保留；账单、退款和审计记录沿用独立业务保留要求，不跟随来源删除一起清空。需要账户注销及更严格的个人数据删除规则时，应作为明确业务流程补充，不能用清空整个数据库代替。

来源移除操作会停用来源、移除其增强指标、撤下属于该来源的独立页面并记录审计。独立采集的关联仓库、已发邮件和账单保留，避免错误删除其他合法来源的数据。

## 7. 本地验证和部署后检查

新增回归覆盖事务回滚、暂存发布、租约 / worker 替换、持久队列、百项诊断、来源权限 / 移除、robots、指标比较、产品家族、可逆审核、安装说明来源、图片保留、保存筛选 / 阈值、全局邮件预算、不可变图与重试内容、账户接口隔离和管理员异常处理。完整 `npm test` 共 90 项通过，`npm run build` 通过；新增阶段回归共 23 项。

`qa/performance/isolated-demo.json` 是隔离 Demo 的 21 个公开路由、每路由三次请求，包含六类榜单 / 筛选 / 图表、搜索、类型和价格。记录 MISS / HIT 是服务端缓存状态，不证明数据库冷启动，也不能用三个样本推断生产 P95 改善百分比。

服务器更新 API 和 scheduler，**不清空数据库**：

```bash
cd ~/trend-top
git pull
./deploy.sh -d --build
```

若脚本报 `required file not found`，先用 `file deploy.sh` / `head -1 deploy.sh` 检查 shebang 与 CRLF，确认后可用 `sed -i 's/\r$//' deploy.sh` 修复本地脚本换行，再执行；不要因此删除数据库卷。

使用既有 `deploy.sh` 读取配置后，在同一 shell 中为生产接口保存对照：

```bash
docker compose exec app node scripts/performance-baseline.mjs --base http://127.0.0.1:3001 --repeat 10 --phase normal --output /tmp/normal.json
docker compose exec app node scripts/performance-baseline.mjs --base http://127.0.0.1:3001 --repeat 10 --phase hot --baseline /tmp/normal.json --output /tmp/hot.json
# 后台发起采集并确认 operations 显示 collect 正在运行，再测：
docker compose exec app node scripts/performance-baseline.mjs --base http://127.0.0.1:3001 --repeat 10 --phase collecting --baseline /tmp/normal.json --output /tmp/collecting.json
```

Compose 解析需要现有部署配置中的数据库密码；若独立 shell 未加载配置，使用服务器既有部署配置加载方法，不把密码写进报告或命令历史。输出在容器临时目录，需要另存用于长期比较。`phase` 只是操作者标签，工具不会自行证明采集正在运行。冷启动测试须单独记录 API / 数据库状态；不要为了基线在生产盲目清缓存或重启数据库。

上线后首次新采集才产生生产候选轨迹；后台审核清理来源及异常投递，使用十到二十个真实 Pro 用户观察相关性、发信稳定性、节省时间和续费原因。现有订阅状态计数及主动反馈人数不能叫续费率。实际新鲜度、覆盖率和留存结论应来自运行记录。
